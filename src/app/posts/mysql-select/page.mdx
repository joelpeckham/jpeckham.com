## The list query that ignored the index you just built

`GET /api/orgs/:orgId/tickets?status=open&updated_after=2026-01-01`

Article [03](/posts/mysql-indexes/) left you with a respectable composite. Then the handler does something like this:

```php
Ticket::query()
    ->where('org_id', $orgId)
    ->where('status', 'open')
    ->whereDate('updated_at', '>=', '2026-01-01') // looks friendly
    ->get(); // SELECT *
```

Eloquent is being helpful. `whereDate` wraps the column. `get()` asks for every column, including a fat `body` TEXT you never show in the inbox table. Same product filters, worse plan, and a lot more bytes than the UI needs.

The fixed shape keeps the API contract and stops fighting the index:

```php
Ticket::query()
    ->select(['id', 'public_id', 'status', 'assignee_id', 'subject', 'updated_at'])
    ->where('org_id', $orgId)
    ->where('status', 'open')
    ->where('updated_at', '>=', '2026-01-01')
    ->limit(50)
    ->get();
```

```sql
SELECT id, public_id, status, assignee_id, subject, updated_at
FROM tickets
WHERE org_id = ?
  AND status = 'open'
  AND updated_at >= ?
LIMIT 50;
```

(`ORDER BY` belongs in the pagination article, coming later in the series. I'm leaving it off on purpose.)

This is post four of [Learn MySQL](/projects/mysql/). [Types](/posts/mysql-schema-types/) shaped the columns. The [primary key](/posts/mysql-primary-keys/) clustered the table. [Composites](/posts/mysql-indexes/) gave list endpoints a path. Today is whether your `WHERE` and select list let that path get used.

## Filter × project

Every `SELECT` answers two questions: which rows survive, and which attributes leave the server?<Cite n={1} /><Cite n={2} /> Apps feel both. Filter work is pages read while finding matches. Projection work is bytes copied, sent over the network, and parked in the buffer pool when you hauled a wide row for a skinny card UI.

InnoDB still finds rows the way articles 02 and 03 described: clustered descent for `WHERE id = ?`, secondary descent plus bounce for org/status/date filters.<Cite n={3} /> This article is about not disabling that machinery with a friendly-looking function, and not asking for the novel when you needed the headline.

## WHERE the optimizer can use

**Sargable** means the engine can compare an indexed column to a known constant or range without transforming every row's column value first. After you learn it, "index-friendly" is usually enough.

Range-eligible shapes on a B-tree include equality, `IN`, `IS NULL`, inequalities, `BETWEEN`, and `LIKE 'prefix%'` when the pattern is a constant that does not start with `%`.<Cite n={4} /> Leading wildcards (`LIKE '%refund%'`) are not a range driver on that column. Wrapping the column in `YEAR()`, `DATE()`, `LOWER()`, or arithmetic usually isn't either.

The function rule is worth thirty seconds of *why*, because it looks like optimizer pettiness and isn't. The index stores `updated_at` values, sorted. It does not store `YEAR(updated_at)` anywhere. A B-tree can seek to "the first entry ≥ 2026-01-01" because that's a position in the sort order; it cannot seek to "entries whose year is 2026" without computing the function on values it hasn't read yet. So MySQL reads them all. Rewrite the predicate as a range on the stored value and the same sorted tree answers the same product question at index speed.

Constants on the *right* are fine. `WHERE id = POW(2, 3)` can still be a point lookup after constant folding. Nondeterministic junk like `WHERE id = FLOOR(1 + RAND() * 49)` cannot.<Cite n={5} />

One nuance before you poke the demo: `YEAR(updated_at)` on a composite that already has `org_id` and `status` equalities often still shows `ref` on those two parts — the date column is what freezes. Play the scan pointer: it walks every open leaf entry instead of seeking a 2026 range. That is the footgun, not a full table scan.

<SargabilityDemo />

<Takeaway>
Bare column on the left. Play seek vs scan: a function on the column forces the pointer to visit every candidate leaf.
</Takeaway>

Those `ref` / `range` / `ALL` labels are teaching shorthand, not a promise from `EXPLAIN`. Steal the rewrite table:

| Bad | Better |
| --- | --- |
| `YEAR(updated_at) = 2026` | `updated_at >= '2026-01-01' AND updated_at < '2027-01-01'` |
| `DATE(updated_at) = '2026-07-24'` | `updated_at >= '2026-07-24' AND updated_at < '2026-07-25'` |
| `whereDate('updated_at', $day)` | range on the bare timestamp |
| `LOWER(email) = LOWER(?)` | store canonical email, or rely on a case-insensitive collation and `email = ?` |
| `subject LIKE '%refund%'` | prefix `LIKE` if you can; otherwise fulltext / search service later |

## Functions on columns (Eloquent edition)

`whereDate`, `whereYear`, and friends read like product language. They compile to functions on the column. Prefer:

```php
->where('updated_at', '>=', $start)
->where('updated_at', '<', $end)
```

For email lookups, don't `LOWER(email)` on every request if `utf8mb4_0900_ai_ci` already gives you case-insensitive equality (house default from article 01). Canonicalize on write when you need a stricter rule. Generated columns and functional indexes exist; that rabbit hole comes later in the series. For now: bare column on the left, bind param on the right.

## Projection: stop selecting the novel

`SELECT *` is fine in a scratch session. In a list handler it couples your JSON to every future column and hauls `TEXT` / `JSON` / secrets you never render.<Cite n={6} /><Cite n={7} /> Wider rows mean fewer rows per InnoDB page, so the same filter touches more I/O even when the index match is perfect.

List endpoints want card columns. Detail endpoints can ask for `body`. Same table. Two jobs.

<ProjectionDemo />

<Takeaway>
List endpoints want card columns. Fat `SELECT *` means fewer rows per page and more pages for the same `LIMIT`.
</Takeaway>

If the select list ever fits entirely inside a secondary index, MySQL may answer from the index without bouncing to the clustered row. That is a covering index.<Cite n={3} /><Cite n={8} /> Designing for it gets a whole article later in the series. Today, listing columns is how you keep that door open and stop shipping kilobytes of `body` to an inbox table.

## List vs detail

| Endpoint | Typical shape | Hope |
| --- | --- | --- |
| `GET /tickets/:id` | `WHERE id = ?` | clustered point lookup |
| `GET /tickets?public_id=` | `WHERE public_id = ?` | unique secondary + bounce |
| `GET /orgs/:orgId/tickets?…` | equalities + range + narrow select | secondary `ref` / `range` on the composite |

Detail can afford a wider row. List should not silently be detail. In Eloquent that means `select(...)` / `toApiArray()` driven by the DTO, not `Ticket::all()` vibes with a `where` tacked on.

## Prefix length for *this* query

Article 03 taught leftmost prefix on the index you build. Here the index is fixed; the predicates move. Equality on left parts, then one range; skip a middle column and the walk stops.<Cite n={4} />

<PrefixLengthDemo />

<Takeaway>
With the index fixed, predicates decide how much left prefix lights. Gaps and mid-key ranges stop the walk.
</Takeaway>

When you peek at `EXPLAIN` later, `key_len` is the rough "how much of this key did we use?" number. Fluency comes later in the series. For now, if your filters don't light the prefix you expected, fix the `WHERE` before you add another index.

## Index condition pushdown (quick)

Sometimes MySQL can test extra conditions on columns that appear in the index *before* it reads the full clustered row. The docs' classic shape is an index on `(zipcode, lastname, …)` with `zipcode = ?` driving access and an awkward `lastname LIKE '%…%'` checked on the index tuple when possible; a filter on `address` still needs the row.<Cite n={9} />

In `EXPLAIN`, `Using index condition` means that pushdown happened. It is not the same as `Using index` (covering / index-only). ICP is a consolation that reduces row reads. Covering is the design where you needed fewer row reads in the first place. We'll design for covering when that article lands.

## Eloquent patterns

The footgun gallery:

```php
// Bad: function on column + star projection
Ticket::where('org_id', $orgId)
    ->whereYear('updated_at', 2026)
    ->get();

// Better: bare column, explicit list columns
Ticket::query()
    ->select(['id', 'public_id', 'status', 'assignee_id', 'subject', 'updated_at'])
    ->where('org_id', $orgId)
    ->where('status', 'open')
    ->where('updated_at', '>=', $start)
    ->where('updated_at', '<', $end)
    ->limit(50)
    ->get();
```

Log SQL in local (`DB::listen` / Telescope). If you see `date(updated_at)` or a naked `select *`, fix the builder, not the server.

Unsupported filter combos on a public API can be a 400. A table scan is not a product feature.

## EXPLAIN previews (not fluency)

On staging data that looks like prod:

```sql
EXPLAIN
SELECT id, public_id, status, subject, updated_at
FROM tickets
WHERE org_id = 42
  AND status = 'open'
  AND updated_at >= '2026-01-01';
```

On a healthy tickets table with `idx_org_status_updated (org_id, status, updated_at)`, a tabular `EXPLAIN` often looks roughly like this (columns trimmed):

| id | select_type | table   | type  | possible_keys            | key                      | key_len | ref         | rows | Extra |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | SIMPLE | tickets | range | idx_org_status_updated | idx_org_status_updated | 10      | const,const | 820  | Using index condition |

Read it left to right: `type = range` (friend), `key` names the composite you meant, `key_len` says how much of that key participated, `rows` is an estimate, and `Extra` here is ICP — not covering (`Using index` would mean index-only).<Cite n={10} /><Cite n={11} /> Contrast that with the bad list below (`YEAR(updated_at)`): you may still see a `ref` on `org_id`/`status` with a shorter `key_len` and no useful range on the date part. We'll read these properly in the EXPLAIN article. If `key` is NULL after you added what you thought was the perfect index, check for functions on columns before you assume MySQL is haunted.

`ANALYZE TABLE` keeps stats from lying after big loads. One sentence; ops depth later.<Cite n={12} />

## Worked schema (tickets, continued)

```sql
CREATE TABLE tickets (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  public_id     CHAR(26) NOT NULL,
  org_id        BIGINT UNSIGNED NOT NULL,
  status        ENUM('open','pending','resolved') NOT NULL,
  assignee_id   BIGINT UNSIGNED NULL,
  subject       VARCHAR(200) NOT NULL,
  body          TEXT NULL,
  updated_at    DATETIME(6) NOT NULL,
  created_at    DATETIME(6) NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uq_tickets_public_id (public_id),
  KEY idx_org_status_updated (org_id, status, updated_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

Detail:

```sql
SELECT id, public_id, org_id, status, assignee_id, subject, body,
       updated_at, created_at
FROM tickets
WHERE id = ?;
```

List (good):

```sql
SELECT id, public_id, status, assignee_id, subject, updated_at
FROM tickets
WHERE org_id = ?
  AND status = ?
  AND updated_at >= ?
LIMIT 50;
```

List (common mess):

```sql
SELECT *
FROM tickets
WHERE org_id = ?
  AND status = ?
  AND YEAR(updated_at) = ?;
```

## Checklist before you merge the handler

- Detail by id uses PK equality (or a unique secondary you meant); list is not secretly detail
- List filters are sargable: bare column on the left, constants/binds on the right
- `whereDate` / `whereYear` / `LOWER(column)` got rewritten or justified
- Composite left-prefix matches the filters you send (article 03)
- Projection is intentional: no `SELECT *` on list endpoints; `body` stays out
- OR / `q=` search has a real strategy, not hope
- You glanced at `EXPLAIN` key/key_len on prod-shaped data
- You did not "fix" a bad WHERE with `LIMIT` alone (pagination semantics get their own article)

A perfect filter still hurts if you `ORDER BY` something unindexed or `OFFSET` into oblivion. That's where the series goes next: sorting, LIMIT, and pagination, then joins that multiply rows. Those articles are in the works; the [series page](/projects/mysql/) is where they'll appear.
